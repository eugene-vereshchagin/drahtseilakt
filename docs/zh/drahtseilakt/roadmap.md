# 路线图

这个分支接下来要做什么、按什么顺序做，以及怎样判断每一步已经完成。各项选择背后的理由写在
[decisions.md](decisions.md) 里。如果你要接手这项工作，请从这里开始。

2026-11-01 的状态：阶段 0 已结束（decisions.md，"Everything from scratch, in Rust"）。新引擎的第一个通宵就让第 1
关可以玩了，超前于阶段顺序：

- **阶段 1**：读取器能读取游戏的每个文件和全部约 600 张地图，每个场景对象都能解码。
  一个变异测试会破坏玩家文件中解压后的部分，并在其上运行所有解码器
  （crates/level/tests/mutations.rs，用 `cargo test` 运行）。尚缺：cargo-fuzz 目标（需要 nightly 工具链和
  libfuzzer，尚未安装）、Building Blocks 清单、移除上游的 C 代码。
- **阶段 2**：关卡及其天空显示在屏幕上，任意尺寸和宽高比，与原版一样在 gamma 空间中计算光照
  （原版的固定管线公式：自发光 + 环境光 + 漫反射，再乘以纹理，再加上高光；关卡没有自己的灯：光是 Gameplay.nmo 的定向光 Light_Ingame，颜色取自关卡表，环境光为 base.cmo 的 0x0F），3D
  精灵（额外分的银色小球）、色键纹理、反射（TexGen）和材质通道
  （圆顶的蓝色），球在其下方地面上的圆斑阴影（TT Simple Shadow）。主菜单和关卡菜单
  使用原型自己的字体；调试模式下有自由相机。游戏内
  界面与原版相同：它的分数框和生命球，分数使用游戏自己的字体。菜单
  看起来和原版一样（它的按钮、深色横条和字体）。关卡结束画面按原版的方式
  计算分数。菜单的 3D 场景（MenuLevel）在菜单后方
  转动，相机沿其曲线绕行。菜单就是原版的界面，用的是这份游戏拷贝自己的文字，默认为经典模式，
  另有扩展模式（[menu.md](menu.md)）：暂停、死亡和结束菜单，带姓名输入的高分榜，
  关卡解锁，从地图文件夹加载的自制关卡。石球在菜单场景中沿着录制好的路线滚动。游戏内相机像原版那样跟随（两个弹簧、250 毫秒的视角旋转、抬升；与 C 版游戏对比测得）。短暂的光照与原版脚本一致：
  最后一关的闪电及其雷声，新球的蓝光。
- **阶段 3**：球的物理是 IVP 的，从上游的 C 代码移植而来（crates/ivp），并与 C 版
  游戏对照检验：木球和石球的直线推动，以及第 1 关上一条 17 秒的路线，误差分别在 0.1
  和 0.8 单位以内。每块地面、每根轨道和每个挡块都使用原版赋予它们的同一种材质（摩擦 0.7，
  弹性 0.3；Levelinit 的 Physicalize_Floors，第 13 关的扩展包也一样）；它们只在
  碰撞组上有所不同。
- **阶段 4**：来自关卡各组的规则（起点、重置点、检查点、额外分和额外生命、变球器、
  坠落、终点）；回放会被录制，每关保留最好的一次。小节、圆顶和关卡开场
  与 C 版游戏一致，变球器的动画（圆环、横杆、球的变换）也是如此。第 1 至 12 关的模块由
  它们的物理部件和关节构成，与 C 版游戏相同，终点的气球也像 C 版游戏中那样把球带走。
  风扇的上升气流会托起纸球；秋千和沙袋的摆动与 C 版游戏一致；石球会压断木板
  桥。声音按原版的 Sound_Manager 和 Music_Manager 的方式生成：事件音效、球的撞击和按
  地面材质区分的滚动声、关卡音乐。靠近风扇时能听到嗡嗡声，木板桥的绳子会断裂。菜单可以设置音效和音乐音量。
  粒子按原版的模块方式生成：起点和检查点的火焰、额外分的
  闪光和拖尾、风扇的风、额外生命的嘶嘶声效果。第 13 关（2004 年的 SuDu 扩展包，按其 readme 的说明安装到
  玩家的拷贝中）可以加载并游玩；完整的基础游戏共十三关。在变球器中旧球会碎成碎片（Balls.nmo 的爆炸脚本：
  碎片是球所在碰撞组中的物体，被向上推出，留在原地 20 秒（Gameplay.nmo 的 Fadeout Manager）或直到失去球，然后淡出）；在碎片之前录制的回放（格式 1）播放时不带碎片，在 20 秒规则之前录制的回放（格式 2）中碎片会一直留到失去球。检查点按其名称顺序（PC_TwoFlames_01、_02……）开启各区段，无论关卡的组以何种顺序列出它们（第 11 关和第 12 关的顺序是乱的）；此前录制的回放（格式 3）保持组内的顺序。散落的物体（箱子、纸球、圆顶）由其模块文件中的对象（PH/P_Dome.nmo 的 `P_Dome_MF`）生成，与原版一致，而不是由关卡中较粗糙的占位物生成；此前录制的回放（格式 4）仍使用占位物。球出现时和碎裂时会冒出一团烟（BallParticle_Frame script）。
- **阶段 6**：开放格式 v1，带导出和导入；第 1 关往返转换后完全一致。导出的关卡是完整的：它带有自己的设置（音乐、光照、奖励、教程、最后一关），并在其 `game/` 文件夹中带有自己的模块、球、变球器、天空、粒子、阴影和声音，因此除了界面之外不需要拷贝中的任何东西即可游玩。项目所有者在第 1、3、5、7、9 关的完整通关记录（tests/replays/）在 `.nmo` 和其导出版本上产生相同的事件（crates/game/tests/open_format.rs），在只含界面文件的拷贝上也是如此。


## 阶段 0 — 在编写后端之前评估 Ballanced

[Ballanced](https://github.com/doyaGu/Ballanced)（作者 doyaGu，也是 BallanceModLoaderPlus 的作者）从源码重建了整个
Virtools 运行时，与原版逐模块对应：`CK2`、`VxMath`、基于 SDL_GPU 的 `RenderEngine`、
包括 `physics_RT` 在内的完整 Building Block 库、插件、SDL3 输入和声音管理器，以及
`Player`。许可为 MIT（仓库）和 Apache-2.0（Building Blocks），因此其代码可以在这个 GPL 项目中使用。
它有适用于 Linux、Windows 和 macOS（x64 和 ARM64）的 CMake 预设，以及在 Linux 上运行测试的 CI，但
唯一的发布版本（0.1.0）只支持 Windows。如果它的 Linux 构建可用，阶段 1 可能在那里已经完成了，而且它完整的
Building Block 库比我们只面向本游戏的那一套更适合自制地图。目前还没有人为我们在 Linux 上运行过它。

在项目所有者的机器上，用他自己的游戏拷贝：

1. 用 `cmake --preset linux-x64-runtime` 构建默认的 `sdl` 分支（递归拉取子模块；SDL3 来自
   发行版，或从固定的发布版本构建）。
2. 运行并检查：能否启动；能否通关一个关卡；球的手感是否与原版一样；它如何处理
   宽屏和高分辨率；能否加载几张自制地图。
3. 把运行了什么、看到了什么记录在本文件中。

然后做出决定，并记录在 decisions.md 中：

- **留下**：继续使用 OpenBallance，按原计划进行阶段 1；
- **迁移**：把分支迁移到 Ballanced 上 — 计划不变，阶段 1 缩减为那里所缺的部分；
- **借用**：继续使用 OpenBallance，并采用 Ballanced 的部分内容（用于地图的 Building Blocks、SDL3 宿主）。

### 目前的结果（2026-10-30）

项目所有者的机器：Debian 13、GCC 14.2、CMake 3.31、Ninja、NVIDIA RTX 3060（驱动 550）、X11 上的 KDE。Ballanced
`sdl` 分支，提交 `ececf94`，预设 `linux-x64-runtime`。

- **SDL3。** Debian 13 自带 3.2.10；Ballanced 需要 3.4.8 或更高版本。从发布的 tarball 构建了 3.4.8，
  已验证 GPG 签名（Sam Lantinga），sha256 `e9fff7467fb60f037e6708da18b25560649e4c63edc2a69bb871b960d9cbfbba`。
- **构建。** 配置和构建都很干净；只有一个 GCC 警告（`XClassArray.h` 中的 `-Wfree-nonheap-object`，
  内联到 `CKSkin.cpp` 中），很可能是误报。输出目录为 25 MB，通过 `BALLANCE_ASSETS_ROOT` 复制进游戏数据后
  为 162 MB。
- **网络。** 运行时没有任何网络代码。构建会从 notofonts 仓库的 `main` 分支下载 Noto 字体：
  有 sha256 校验，但没有固定到某个提交，所以上游字体一更新，构建就会失败。
  `VXMATH_FONT_DIR` 可以用本地副本离线构建。
- **运行。** SDL_GPU 运行在 Vulkan 上。主菜单正常，第 1 关通关；球的手感与原版一样（项目所有者的
  判断）。窗口在运行中从 1280×720 调整到 3840×2069，没有问题；画面保持 4:3，
  两侧加黑边。两次会话，分别为 1.5 分钟和 7 分钟，都正常结束，日志中没有任何内容。
- **宽屏。** `--unlock-widescreen --unlock-high-resolution` 只是在游戏脚本提供的分辨率列表中添加宽屏模式；
  1920×1080 能被接受，但关卡相机仍然是 4:3，渲染器会给画面加黑边。
  然而 HUD 是相对整个窗口布局的，所以在宽窗口中它会位于画面旁边，
  部分落在黑边上。真正的宽屏没有实现；在原版中这需要一个 BML mod。
- **自制地图。** 一个测试工具（在仓库之外）把地图放到一个临时的游戏根目录拷贝中替换第 1 关，
  在私有的 Xvfb 显示上用软件 Vulkan（lavapipe）运行 Player，用 xdotool 操作菜单，
  并截取游戏窗口。五张样本地图，大小从 74 KB 到 4 MB，全部加载并运行，日志中
  没有任何内容。完整的地图集（579 个 `.nmo` 和 19 个压缩包）尚待运行。
- **Bug。** HUD 中生命计数器的括号被画在很靠左的位置，并在游戏过程中漂移（在
  最大化的 3840×2069 窗口中看到）。在 640×480 下 HUD 与原版完全一致，包括那个小小的左括号，
  所以问题出在非 4:3 窗口以及上面所说的 HUD 布局。尚未向上游报告。
- **文字排版。** 教程文字的换行与原版不同（原版整行显示的一行被
  拆成了两行）：字形度量或文本框宽度有差异。
- **参照。** 项目所有者的原版游戏运行在 Wine 下（Wine 10，独立的 prefix，游戏的私有拷贝，
  使用内置的 `ddraw`/`d3dimm` 而不是附带的 dgVoodoo），在私有的 Xvfb 显示上，用同样的方式
  脚本化操作。有两个陷阱：Xvfb 只有一种视频模式，所以屏幕必须是游戏的模式，否则游戏
  会弹出对话框要求选择；而软件 OpenGL 需要 `WINE_LARGE_ADDRESS_AWARE=1`，否则这个 32 位
  进程会耗尽地址空间，`base.cmo` 加载失败。
- `Player --help` 不是一个选项：它会被忽略，游戏直接启动。
- **测试**（`linux-x64-tests`，967 个测试，在 Xvfb 上用 lavapipe 运行）。GCC：全部通过，但有 36 个 CK2 测试
  并行运行时失败，串行运行时通过 — 它们共享某种资源；这是测试隔离问题，不是引擎
  bug。Clang 19：只有用 `lld` 才能构建（RenderEngine 使用 LTO，而 GNU ld 无法读取 Clang 的 bitcode）；两个
  `RectTransformReferenceTest` 用例因浮点异常标志失败（未使用的 SIMD 通道中触发了 FE_INVALID），
  在 GCC 下则通过。可选的 GPU 测试除一个在 lavapipe 上的精确深度像素测试外都通过，该测试仍
  有待在真实硬件上运行。GoogleTest 按标签而不是按提交拉取。
- **离线构建。** 把 `VXMATH_FONT_DIR` 指向我们自带的字体（`assets/fonts`）并设置
  `FETCHCONTENT_FULLY_DISCONNECTED` 后，Ballanced 可以在无网络的情况下配置和构建。
- **原版关卡。** 十二关中的每一关，放到第 1 关的位置后，都能加载并运行，日志中没有任何内容
  （只测了加载：没有人把它们玩通）。
- **尚未检查：** `--unlock-framerate`、完整的地图集。

## 阶段 1 — 基础和 Virtools 文件读取器

目标：一个干净的 Rust 代码库，能安全地读取游戏和社区制作的每一个 `.nmo` / `.cmo`。

- 本仓库中的一个 cargo workspace（根目录下的 `Cargo.toml`，crate 放在 `crates/` 中）。依赖在
  `Cargo.lock` 中固定版本并 vendor 到本地，因此可以离线构建；每个 crate 在加入前都要经过检查
  （确实存在、有人维护、许可证与 GPL-3.0 兼容）。
- 读取器：文件头、压缩部分、对象表、状态块、管理器数据、嵌入文件。
  输入是不可信的：每次读取都做边界检查，大小、数量和嵌套深度都有上限，格式错误的文件
  会以一个指明偏移量的错误失败 — 绝不 panic。读取器中不使用 `unsafe`。
- `nmo-dump`，一个命令行工具，打印文件中包含的内容：对象、组、网格、材质、纹理、
  行为图。
- 测试：由测试自己构造的合成文件；fuzz 目标（cargo-fuzz）；针对
  玩家拷贝（`OPENBALLANCE_DATA`）、`levels/` 中的十三个关卡以及地图合集
  （`OPENBALLANCE_MAPS`）的本地测试。
- **清单**：在所有地图中，出现了哪些对象类、组名、Building Blocks 和参数类型，
  各出现多少次。它决定阶段 4 和阶段 5 的顺序。
- 上游的 C 代码移出构建（历史记录中保留）；`docs/` 作为参考资料保留。

完成标准：游戏的每个文件和全部约 600 张地图要么完整解析，要么以干净的错误失败；
fuzzing 运行了足够长的时间且没有发现问题；清单已经完成。

## 阶段 2 — 第一个关卡显示在屏幕上

- 窗口、输入和音频宿主；基于 wgpu 的渲染器（Vulkan、Metal、Direct3D 12）。窗口是来自
  SDL3 绑定还是来自纯 Rust 的 crate（winit、gilrs、cpal），在开始时决定并记录下来。
- 用玩家的纹理，从第 1 关的 `.nmo` 绘制出来：网格、材质、透明、天空、灯光。
- 从第一帧起支持任意分辨率和宽高比，不再是 4:3：3D 视图使用真实的宽高比；
  2D 布局在中间保持 4:3 的 640×480，靠边的元素锚定到边缘；支持 HiDPI；最高 4K。
- 从一开始就采用固定的 60 Hz 模拟 tick，渲染做插值。
- 可以在任意关卡中飞行的自由相机。

完成标准：十三个关卡都可以飞行浏览，并且看起来与原版一样（由项目所有者判断，画面
与 Wine 下的原版对比）。

## 阶段 3 — 球

- **参照**：把 Wine 下的原版游戏当作测量仪器 — 脚本化输入，从运行中的游戏读取每个 tick 球的位置
  和速度，而不修改它的文件（具体方法在
  本阶段中摸索出来）。录制的场景成为参照轨迹。
- **自己的物理**，从零开始：三种球在静态几何体上运动，摩擦、阻尼和重力按
  测量结果设定；箱子和移动物体在阶段 4 中跟进。碰撞几何体与原版一致，逐个
  多边形对应。
- 球的操控和游戏相机，与原版一样。

完成标准：参照场景保持在容差范围内，并且项目所有者滚过第 1 关后认为
球的手感是对的。

## 阶段 4 — 游戏

- 规则以原生方式实现，由关卡的数据（其分组约定）驱动：起点、小节、检查点和
  重置、生命、分数、额外分和额外生命、变球器、物理和移动物体、
  终点。菜单、HUD（适配任意宽高比的布局）、音效、音乐。
- **回放**：每个 tick 的输入日志，采用有文档、有版本号的文本格式，关卡由其哈希值标识。
  无头回放会检查检查点、终点和分数。回放只包含我们自己的输入，所以它们放在
  仓库里（`tests/replays/`），并在 CI 中运行。
- 第 13 关：2004 年的 SuDu 扩展包，属于基础游戏的一部分。玩家按照其
  readme 的说明把它安装到自己的拷贝中（它替换 Gameplay、Menu、MenuLevel、Levelinit、Sound 和 PE_Balloon，并添加 Level_13）。

完成标准：十三个关卡都可以通关，并且每关都有一个能通过的回放。

## 阶段 5 — 自制地图

- 每个用户数据目录中的一个地图文件夹，以及游戏内的列表（标题、作者、来自
  目录的难度）。
- 遵循标准约定的地图通过阶段 4 的原生规则游玩。
- 带有自己 Virtools 脚本的地图：一个行为图解释器，Building Blocks 按
  清单给出的顺序实现。需要我们缺少的模块的地图不会运行到一半：它会按
  模块名称和 GUID 报告出来，并标记为不支持。
- **游戏配置**：*经典* — 只有原版游戏（十二个关卡和第 13 关，原版规则；回放
  和纪录只在这里计入）；*扩展* — 第三方内容，风险由玩家自负，并有明确的
  警告：自制地图、材质包、模组。模组是我们自己的纯数据格式：由引擎构件的固定库组成的规则，
  由我们的运行时解释，绝不是代码（[mods.md](mods.md)）；BML mod 是 Windows DLL，永远不会被加载。
  两种模式的菜单：[menu.md](menu.md)。

完成标准：大多数地图可以游玩；报告列出其余地图，并逐一说明原因。

## 阶段 6 — 开放关卡格式和转换器

- 一种开放、有文档的关卡格式：几何体用 glTF 2.0，纹理用 PNG，声音用 Opus，摆放位置和属性放在
  一个文本文件中。规范放在 `docs/` 中。
- 一个从 `.nmo` 转换的转换器，由玩家在自己的文件上运行。引擎永久支持这两种格式
  （decisions.md）。
- 测试：每个原版关卡和它转换后的副本，在同一个回放下给出相同的轨迹。

## 阶段 7 — 画面和附加功能

- **圆的东西看起来是圆的**：球以解析方式绘制；使用平滑法线的逐像素光照；
  对轨道和管道做法线引导的曲面细分。仅限视觉：物理仍基于原版的多边形。采用哪些
  技术、做到什么程度，在试过之后与项目所有者一起决定。第一步已完成：toolbox 为重制关卡中弯曲的网格生成由
  曲面点法线三角形构成的外观并写入关卡（toolbox 的 smooth.rs；关卡是平面着色的，因此夹角小于 40 度的面先被视为同一个平滑曲面），只弯曲法线像圆弧那样弯曲的边，因此轨道保持笔直；重制的 Level_NN
  使用第 NN 关的设置（光照、音乐、最后一关的闪电）。第二步已完成：凹凸细节。toolbox 从每个受光照纹理自身的图像生成法线贴图（把细微的亮度变化当作高度：铆钉、木板缝、绳子），渲染器据此改变光照；没有法线贴图的关卡绘制得与之前完全相同。默认关闭（`--relief S`）：从图像推测出的凹凸会加深每一条裂缝和缝隙（项目所有者：“像被酸蚀过”）；真正的凹凸需要图像之外的高度信息。砖砌已完成：纹理显示混凝土中的砖砌（地板的砖带）时，toolbox 按颜色而非亮度识别砖块，使砖块凸起、灰缝凹下，渲染器以视差遮挡（parallax occlusion）绘制这一高度；始终开启，木材、石材和金属不受影响。
- **本地纹理增强**：玩家在自己的拷贝上运行的脚本，用来放大纹理（最高 4K）；
  仓库中只保存处理流程及其参数，绝不保存结果。
- **把回放渲染成视频**：离线逐帧渲染，任意分辨率最高 4K，带声音。没有项目所有者的命令，
  什么都不会上传。

## 玩家用 mod 添加了什么

对三十个 BML/BML+ mod 的静态调查（只看字符串和 readme；从不运行 mod）显示了玩家
缺少什么；完整的逐个 mod 的表格以及我们对每个的处理见 [mods.md](mods.md)。已完成（2026-11-03）：我们自己的
纯数据模组格式及其运行时、Mods 界面，以及用该格式编写的十个内置模组（粘性球、物理实验室、动态视野、自由视角、
带分段的小节计时器、信息叠加层、快速重开、截图、灵魂轨迹、全黑）；被模组改变的游玩在其回放中标记为 modded。
排队中：同伴（两个球）、随转动的视角转向、诱饵球、游戏时长统计。纳入基础引擎的：练习工具（出生点和小节选择、快速重开、每个小节最佳成绩的
幽灵球、分段计时和实时计时器）；带快进的确定性输入录制和回放（TAS）；
信息叠加层（球的位置、本小节剩余的额外生命和额外分）；自由相机和视野
设置；不设固定的小节数量上限，以及供地图脚本使用的事件钩子；重力、时间因子和游戏速度作为
测试用的设置；截图。以后再做或可选的：动态视野、鼠标旋转相机、两个球、
新的球种和部件、挑战模式（全黑、诱饵球）。那些 mod 所绕开的原版限制（帧率上限、4:3、低分辨率、八个小节、位图字体、脆弱的变球时机）
不是我们要照搬的；而它隐藏的常量（重力 -20、物理时间因子 2）是要照搬的。

## 贯穿始终

- 安全规则（`CLAUDE.md`）：输入不可信，依赖固定版本并 vendor 到本地，CI action 按
  提交 SHA 固定，并使用最小的 `permissions:`（上游的 workflow 按标签固定，必须修复或替换）。
- 不依赖数据的测试在任何地方运行（单元测试、合成文件、fuzzing）；依赖游戏数据的测试在本地运行。
- 文档使用四种语言。上游仅有英文的文档属于参考资料，除非它变成我们自己的文档，否则不翻译。
